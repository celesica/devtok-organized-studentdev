Get Organized as a Student Developer

Build a Better System for Classes, Projects, and Your Coding Workspace

This guide walks through how to set up an organization system for your school files, your coding projects, and the things you learn on your own. It's built for CS, IT, and engineering students who write code as part of their coursework, and you don't need to be an advanced programmer to follow it.

August 2026 · Jazzy · DevTok Pinas
TL;DR

You don't need a complicated productivity system. You need four main folders, a clear rule for where each type of file goes, a calendar that actually reminds you, and a short routine for when things get messy. Everything here works whether you're starting a term, in the middle of one, or between them.

Your Four Main Folders

What this section covers: The four top-level folders that hold everything you make, and how to decide which one something belongs in.

Why it matters: Most people decide where to save a file at the moment they save it, which is why things end up in Downloads. Decide once, in advance, and saving stops being a decision.

The four folders — click to explore

Studies

Your formal school work — everything tied to your degree that isn't code.

What goes here: subjects, assignments, lecture files, exams · curriculum and grade slips · graduation requirements and student aid documents · thesis or capstone documents · OJT and internship paperwork · school organizations.

NOTEAnything containing code goes in Development instead, including programming assignments. Studies holds the documents, requirements, and submissions.

Development

Anything that involves code. All of it, regardless of where it came from.

What goes here: programming assignments and lab exercises · school software projects and your capstone · practice code from tutorials and online courses · personal projects and experiments · hackathon projects · code you write for an organization.

One rule, no exceptions: if it contains code, it lives here. Not in your school folder, not in a course folder, not on the Desktop.

HOW I DO IT
Development/
├── school/
│   ├── Y2T1/
│   └── Y2T2/
├── learning/
├── personal/
├── hackathons/
├── experiments/
└── archive/
  • school/ — code written for classes, kept by term so it stays findable
  • learning/ — code written while following courses and tutorials
  • archive/ — projects you've stopped working on

Upskilling

Learning you do outside your curriculum. This holds the material you learn from, not the code you write.

RECOMMENDED
Upskilling/
├── web-development/
├── cloud/
├── ai-and-data/
├── design/
├── certificates/
└── resources/

When you look for something later you remember the subject, not the website — and one topic usually spans several platforms.

Upskilling/
├── coursera/
├── udemy/
├── youtube/
├── freecodecamp/
└── certificates/

Works if you're enrolled in a structured multi-course program and think of your learning that way.

Pick one and stay consistent. Mixing both is what makes things hard to find.

NOTECode you write while following a course goes in Development/learning/. Upskilling holds slides, notes, downloads, and certificates.

Career

Documents you'll need when applying for internships and jobs. The only folder that outlives your degree.

Career/
├── resume/
├── certificates/
├── portfolio/
├── applications/
└── interview-prep/
  • certificates/ — copies of anything worth listing, including the ones from Upskilling
  • portfolio/ — screenshots, project descriptions, links
  • applications/ — one folder per company you apply to

Most students only create this when they urgently need it. Make it now, even empty.

The code rule

Anything containing code goes in Development. School assignments, lab exercises, tutorial practice, capstone code, personal projects — all of it, one location, no exceptions. The binary rule cannot be got wrong.

1. Does it contain code? → Development. Stop.

2. Does it stop mattering when the term ends? → Studies.

3. Is it material you're learning from? → Upskilling.

4. Does it outlive the degree? → Career.

SPLITWhen something has both code and documents (assignments, capstone, thesis): code to Development, documents to Studies, plus a short pointer file in Studies noting where the code is. This is the standard pattern, not an exception.

HOW I DO IT

Keeping every line of code in one place is what made this work for me. Before that I had code in course folders, code on the Desktop, and code in Development, and I could never remember which. One location means one place to look.

Key takeaways

  • Four folders: Studies, Development, Upskilling, Career.
  • Anything containing code goes in Development — school, tutorials, personal, org work, all of it.
  • Upskilling by topic works better than by platform for most students.
  • School org files sit under Studies; resume-worthy org work goes in Career.

Organizing Your School Files

What this section covers: A folder structure for coursework, a naming convention, and what to do if you already have years of files scattered around.

Why it matters: School generates your highest volume of files, every term. A structure you set up once and reuse removes almost all the decisions.

The structure

Program → Term → Subject. Keep the inside of each subject simple.

RECOMMENDED
Studies/
└── BS Computer Science/
    ├── Courses/
    │   ├── Y1T1/
    │   └── Y2T1/
    │       ├── Algorithms and Complexity/
    │       ├── Life and Works of Rizal/
    │       └── Software Engineering/
    ├── Curriculum/
    ├── Grade Slips/
    ├── Graduation Requirements/
    └── Organizations/
  • Use this if you don't already have something that works. Other arrangements are in the toolkit.
  • Most subjects only need a few folders inside. Don't create folders you aren't using.
  • Set it up once at the start of each term. It takes a few minutes.
Learn more — term-first vs subject-first

Subject-first (Program → Subject → Term) keeps one subject together across years. Useful if you retake subjects.

Term-first works better for most students because school runs on terms, and because finished terms move out of your way on their own.

Naming files

Instead ofUse
Assignment final v2.docx2026-08-15-algorithms-assignment.docx
Aug 15 notes2026-08-15-lecture-notes.md
stuff2midterm-reviewer
  • Dates: year-month-day. 2026-08-15. Files then sort in date order automatically.
  • No spaces — use dashes. CONVENTION Spaces cause problems in the terminal and in code projects.
  • Be descriptive. The name should still make sense in six months.

What happens at the end of a term

Nothing. The term folder stays exactly where it is.

  • You don't archive it, sort it, or clean it out
  • The only action is creating next term's folder
  • Old work stays where you'd naturally look for it

Why this works: a degree is around twelve terms, so the list never gets long. Organizing by year and term means finished work moves out of your way without you doing anything.

NOTECoding projects are different — they don't end on a schedule, which is why Development/ keeps an archive/ folder.

If you already have years of scattered files

RECOMMENDED

Don't reorganize everything at once. That usually takes longer than expected and gets abandoned halfway.

  1. Create one folder named _UNSORTED_2026-08, with the date in the name.
  2. Move everything loose into it. Don't sort as you go.
  3. Build the new structure beside it, empty.
  4. Use the new structure from now on.
  5. When you need an old file, take it out and file it properly at that point.

After a few months, most of what's left is material you never needed.

NOTEAbout ten minutes, not a weekend. The point is to stop the mess growing, not to fix the past.

Key takeaways

  • Program → Term → Subject, set up once per term.
  • YYYY-MM-DD and no spaces so files sort themselves.
  • Finished terms stay where they are. No archiving step.
  • If you have a backlog, move it aside rather than reorganizing it.
DO

Set up the folders for this term only, and move anything loose into a single dated unsorted folder.

Your Coding Projects

What this section covers: The difference between a folder, a project, an editor workspace, and a repository — plus how much structure a project actually needs.

Why it matters: These terms get used interchangeably, which makes tutorials and instructions confusing. Once you can tell them apart, most of that confusion goes away.

The five layers — build the stack

Each layer answers one question and earns one word. Click Next to add them one at a time.

Layer 1 — The folder

A location on your computer where the files sit.

  • A normal folder, like any other
  • It lives inside Development/ — including for school work
  • Everything below is something added to this folder
NOTEDon't put a coding project inside a synced folder like Google Drive, OneDrive, or Dropbox. Sync conflicts with the tools you'll use and can corrupt the project. On Windows, check whether Documents is syncing to OneDrive — it often is.

Layer 2 — The project

The same folder, once it contains everything needed to run.

  • A README file — plain text saying what this is and how to start it
  • A dependency file — requirements.txt for Python, package.json for JavaScript
  • The code, organized rather than loose
A project is a folder that knows how to run itself.

Layer 3 — Opening it in your editor

When someone says "open the project in VS Code," they mean opening the folder, not a file.

  • Open a file — a text editor with one document in it.
  • Open a folder — the full file list, a terminal pointed at the right location, search across the whole project, and tools that can see how files relate.
NOTEThis is the most common reason a beginner's screen doesn't match the tutorial. Use File → Open Folder.

Layer 4 — Git

A tool that records the history of your project as you work.

  • Each meaningful change is a commit — a snapshot with a short description
  • You can return to any earlier version
  • It replaces keeping final, final2, final-v3 copies

Layer 5 — GitHub

A website where your project's history is stored online.

  • Git tracks changes on your computer
  • GitHub is where you upload that history so others can see it
  • Uploading is pushing; downloading someone else's project is cloning
NOTEGitHub is for code and the files around code. Not general cloud storage — your thesis PDF and lecture slides don't belong there.

Five layers, five words, used interchangeably by everyone. Naming them is most of the fix.

How much structure a project needs

Not every project needs the full setup. Select a type to see what it actually needs.

exercise.py

One file. Does not need: folders, a README, or Git.

assignment/
├── main.py
└── README.md

One folder, README if there are instructions worth keeping. Does not need: a full src/tests split.

project-name/
├── src/
├── README.md
├── .gitignore
└── requirements.txt

Organized folders, README, .gitignore, dependency file, on GitHub. Does not need: shared access or CI.

project-name/
├── src/
├── tests/
├── docs/
├── README.md
├── .gitignore
├── .env.example
└── requirements.txt

All of the above, plus shared access (Section 09). Does not need: anything you're not actually using yet.

  • Adding structure a project doesn't need makes it harder to work on
  • Start small. Adding structure later is easier than removing it
  • You're allowed to have a project that's one file

Moving work up a level

When school or practice work turns out well:

  • Move it from Development/school/ or learning/ into personal/
  • Add a README explaining what it does and how to run it
  • Put it on GitHub
ADVANCED

This matters most at internship time. Work sitting in a term subfolder is work nobody will look at.

HOW I DO IT

What helped me most was checking my own projects the way a stranger would: download it into an empty folder and try to run it using only the README. If that works, it's set up properly.

Key takeaways

  • A folder is a location. A project is a folder containing everything needed to run.
  • "Open the project" means open the folder, not a file.
  • Git tracks changes locally. GitHub stores that history online.
  • Match structure to what the project is for. Small things stay small.

Your Calendar and Tasks

What this section covers: Setting up Google Calendar for your class schedule, deadlines, and everything else you're responsible for.

Why it matters: A printed schedule or a screenshot of your Canvas calendar tells you what's happening. It doesn't remind you, hold your meeting links, or update when something changes.

Why a calendar app instead of a printed schedule

TOOL-SPECIFIC
  • It reminds you. Notifications on your phone before class or a deadline.
  • It holds the details. Zoom or Meet links, room numbers, LMS links, professor names — inside the event, one tap away.
  • It updates. A room change or moved deadline is one edit, not a reprint.
  • It's searchable. Find when an exam was, months later.
  • It's on every device. Phone, laptop, browser.
  • It repeats. Set your class schedule once for the whole term.

We'll use Google Calendar because it's free with any Google account and includes Tasks. Any calendar app with reminders works the same way.

Step 1 — Make separate calendars

Instead of putting everything in one calendar, create a few and give each its own color.

RECOMMENDED
  • Classes — your recurring schedule
  • Deadlines — submissions, exams, defenses
  • Org and events — meetings, activities
  • Personal — work, family, rest

Step 2 — Add your class schedule

Add each class once as a repeating event for the whole term. Click through the fields to build one.

CS 3202 — Algorithms and ComplexityMWF · 9:00–10:00 · repeats to end of term

Step 3 — Set up Tasks

Calendar events are for things happening at a set time. Tasks are for work that needs doing. Google Tasks lists appear inside Calendar, and each list gets a color that shows on the day a task is due.

Suggested lists: Assignments · Study and practice · Exams and quizzes · Group projects · Org work · Personal.

NOTETasks has no labels or tags, so lists are how you separate categories. Keep the number small — six is plenty.

Step 4 — What actually goes in tasks

Add things the day you hear about them, not the day they're due.

TaskGive it a date
AssignmentTwo or three earlier dates, one per step
Practice codingA recurring slot, e.g. Tue and Thu evenings
Quiz or exam reviewStart three or four days ahead
Group project workYour own part, with your own date
Org workWhatever you committed to
Rest and self-careYes, actually schedule it

Break big things into steps. An assignment due in two weeks becomes: outline it, build it, review it. Three tasks with three dates.

NOTEThe due date shouldn't be the first time your system hears about an assignment.

Step 5 — Notifications

  • Classes — 30 minutes before
  • Deadlines — one day before and two hours before
  • Exams — three days before
  • Turn off anything you've started ignoring. Notifications you dismiss without reading are worse than none.
HOW I DO IT

The change that mattered most for me wasn't the color coding — it was putting the meeting link inside the event. Everything else is organization. That one is time you get back every single day.

Key takeaways

  • Separate calendars with distinct colors: classes, deadlines, org, personal.
  • Add classes once as repeating events, with room, link, professor, and LMS link inside.
  • Use Tasks lists for work; add things the day you hear about them.
  • Break large assignments into steps with their own dates.
  • Set reminders you'll actually respond to.
DO

Add this term's full class schedule as repeating events, with the room and meeting link in each one.

Protecting Your Work

What this section covers: Password management, backing up your files, and keeping passwords out of your code.

Why it matters: These are one-afternoon setups that prevent problems which are difficult or impossible to reverse.

Use a password manager

RECOMMENDED

Reusing one password across accounts means one leak exposes all of them. A password manager creates and remembers a different password for every account, so you only memorize one.

Bitwarden is free, works on every platform, and is what I use. 1Password and Proton Pass work the same way.

  1. Create the account with a strong master password you can remember
  2. Save the recovery information somewhere offline
  3. Install the browser extension and the phone app
  4. Change your most important passwords first: email, GitHub, school portal, bank

Turn on two-factor authentication for email, GitHub, and your school portal. Save the recovery codes somewhere that isn't the laptop they protect.

Your school email

Your school email stops working after you graduate, and anything using it as the recovery address becomes hard to recover.

  • Create a personal professional email now
  • Use it for GitHub, LinkedIn, your portfolio, and anything you keep after school
  • Keep the school email for school
NOTETen minutes now, a real problem later.

Backing up your files

Three different jobs. Click a destination to focus it.

Your laptop
The copy you work on
Cloud storage
Studies/
Upskilling/
Career/
Development/ — never sync
GitHub
The history of your code

Do not sync Development/. Sync services conflict with the files Git creates and can corrupt a project. Code is backed up by pushing it to GitHub, which does the job properly.

NOTEIf your only copy of something is on one device, it isn't backed up.

Keys and passwords inside code

When a project connects to another service, that service gives you a key — effectively a password for your app. Click through what usually goes wrong.

API_KEY = "sk_live_51H8xY2..."  # pasted straight in

Step 1 — The key gets pasted into the code and everything works.

# pushed to a public repo
API_KEY = "sk_live_51H8xY2..."  # now visible to everyone

Step 2 — The project goes onto GitHub with the key inside it. Public repositories are scanned automatically for keys.

# current file — key removed
API_KEY = os.environ["API_KEY"]
# ...but the old commit still shows: sk_live_51H8xY2...

Step 3 — Deleting the line later doesn't remove it. Git keeps the history. This is the one nobody knows.

# .env  (stays on your computer)
API_KEY=sk_live_51H8xY2...

# .gitignore
.env

# .env.example  (safe to commit)
API_KEY=

Step 4 — The corrected setup: keys in .env, .env listed in .gitignore, a blank .env.example for teammates.

NOTE.gitignore is also where generated folders like node_modules go. They're large, rebuildable, and don't belong in a repository.

Key takeaways

  • Use a password manager and a different password everywhere.
  • Two-factor authentication on email, GitHub, and school portal.
  • Create a personal professional email before you graduate.
  • Sync Studies, Upskilling, and Career to the cloud. Never sync Development.
  • Code is backed up on GitHub. Keys go in .env, never in the code.
DO

Set up a password manager today and change your email password first.

Setting Up Your Coding Workspace

What this section covers: What a coding workspace is, and what to install so you can actually work.

Why it matters: "Set up your workspace" gets said a lot without anyone explaining what it means. It's your editor, your tools, and your project folder working together.

What a coding workspace is

Three things, not one:

  1. Where your code lives — the project folder inside Development/
  2. What you open it with — your editor, with the folder open, not a file
  3. What's installed — the tools that let the code run

Section 03 covered the first two. This section is the third.

What to install, by job

RECOMMENDED

Install things because you need them, not because a list says every developer has them. Filter by when.

ContainersDockerLater
NOTEEverything in the "Now" row is free and takes one afternoon.

Extensions

TOOL-SPECIFIC

You don't need twenty-five VS Code extensions.

Worth having early: the language extension for what you're learning (Python, or the JavaScript pack) · a formatter (Prettier) · GitLens, if you want a clearer view of your project's history.

Add anything else only when you hit a specific problem it solves. Extensions slow the editor down and most of them you'll never open.

Keeping the workspace usable

  • Close projects you're not working on. One project open at a time.
  • Keep the terminal open at the project folder rather than typing cd repeatedly.
  • Delete leftover test files — test.py, untitled1.js — as you go.
  • If your editor is slow, it's usually extensions or a synced folder.

Group Projects and Shared Repositories

ADVANCED Reference material. Covered live only if there's time.

What this section covers: Setting up a group project so everyone can work on it.

Why it matters: Most group project problems are setup problems, and they're much cheaper to fix in week one than the week before defense.

What usually goes wrong

  • The working version is on one person's laptop and they're unreachable
  • The same file gets passed around in a group chat under different names
  • A teammate can't get the project running, doesn't want to ask twice, and stops contributing
  • The account holding everything belongs to someone who stops responding

Setting it up

On day one, before anyone writes code:

  1. One repository. Everyone gets access immediately.
  2. One person listed as owner, but everyone has full access, so nobody is blocked.
  3. Everyone downloads it and runs it once. Fix problems now, while they're small.
  4. Write the README on day one. It's how a teammate gets started without messaging you.
NOTEThe teammate who can't get it running usually won't say so twice. Checking on day one prevents most uneven-workload problems.

Where a capstone lives

Development
The code, in the repository
Studies
Requirements, forms, adviser feedback, defense slides

pointer.txt in Studies → names where the code is, with the link

Same split as any assignment with both a program and a written component.

Key takeaways

  • Set up the shared repository on day one with access for everyone.
  • Confirm every teammate can run it before real work starts.
  • Capstone code goes in Development; paperwork goes in Studies, linked by a note.

README template

# Project Name

One sentence on what this does.

## What it does
Two or three sentences. What problem it solves, or what
it was built for.

## Requirements
- Python 3.11 (or Node 20, etc.)
- Anything else that must be installed first

## Setup
1. Clone or download this repository
2. Install dependencies:
   pip install -r requirements.txt
3. Copy .env.example to .env and fill in your values
4. Run it:
   python main.py

## Notes
Anything a person would trip over. Known issues, things
that aren't finished.

## Built with
List the main tools or frameworks.

The test: download your own project into an empty folder and set it up using only the README. If that works, it's done.

glossary

Twelve words, defined

FolderA location on your computer where files sit. Nothing special about it.§03
ProjectA folder containing everything needed to run what's inside it: the code, a README, and a list of what must be installed.§03
WorkspaceWhat your editor shows when you open a whole project folder rather than a single file: the file tree, a terminal, and search across everything.§07
Repository (repo)A project that Git is tracking. It holds the files and their history.§03
RemoteA copy of your repository stored online, usually on GitHub.§03
GitThe tool on your computer that records the history of your project as you work.§03
GitHubA website that stores Git repositories online so others can see them and work with you.§03
CommitOne saved snapshot in your project's history, with a short description of what changed.§03
CloneDownloading a copy of a repository from GitHub to your computer.§03
PushUploading your commits from your computer to GitHub.§03
TerminalThe text window where you type commands instead of clicking. Built into VS Code.§07
DependencySomething your project needs installed in order to run. Listed in requirements.txt or package.json.§03
